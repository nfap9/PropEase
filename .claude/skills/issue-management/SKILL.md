# Apartment Ultra Issue 管理

本 skill 用来统一本项目中 GitHub Issue 的创建、补充、拆分、更新与关闭方式，让 issue 成为可靠的任务入口，而不是一句模糊待办。

## 使用目标

- 让每个 issue 都能回答“为什么做、做什么、不做什么、怎样算完成”
- 减少模糊标题、空洞描述和无法验收的问题
- 让后续 Agent 或开发者只看 issue 就能安全开工

## 什么时候必须使用

- 用户要求创建、改写、补全、拆分、整理 GitHub Issue
- 用户描述了需求、缺陷、技术债，希望沉淀成任务
- 用户希望规范 issue 写法、建立 backlog 规则、补验收标准
- 你准备依据某个 issue 开工，但 issue 信息明显不完整

## 核心规则

1. 一个 issue 只承载一个可交付目标。
2. 标题必须包含模块和结果，避免“优化一下”“处理问题”这类空标题。
3. 描述必须能支持执行和验收；说不清完成标准时，不要直接进入实现。
4. 行为变更、跨模块改动、需要测试验证的事项，都要写验收标准。
5. 超出单次小改动范围的工作要先拆分，再安排实施顺序。
6. PR、测试、相关文档都应该能从 issue 中找到线索。

## 标题格式

统一使用：

```text
[模块] 动作 + 结果
```

模块建议从以下集合中选：

- `api`
- `tenant-web`
- `admin-web`
- `mobile`
- `packages`
- `e2e`
- `docs`
- `infra`

标题示例：

- `[tenant-web] 支持账单列表按状态筛选`
- `[api] 修复账单重复生成问题`
- `[e2e] 补齐租约续租流程覆盖`
- `[docs] 更新本地开发启动说明`

避免这些标题：

- `修复 bug`
- `优化一下账单`
- `处理租约问题`
- `增加功能`

## 背景

## 按类型补充信息

### Bug

除了通用模板，再补：

- 实际结果
- 期望结果
- 复现步骤
- 是否稳定复现

### Feature

重点写清：

- 谁会使用这个能力
- 业务价值是什么
- 完成后用户能做什么

### Refactor / Chore

重点写清：

- 当前痛点是什么
- 这次重构或整理的边界是什么
- 如何证明没有引入回归

## 拆分规则

遇到以下情况，先拆 issue 再开工：

- 同时涉及后端、前端、E2E，且每部分都能独立交付
- 同时混合“修 bug”和“顺手重构”
- 单个 issue 无法写出 2 条以上明确验收标准
- 预估需要多个 PR 才能安全落地

拆分后建议保留一个父 issue，用来说明背景与顺序；子 issue 只负责具体交付。

## 执行前检查

在依据 issue 开工前，确认：

- 标题是否明确表达了结果
- 是否写明范围与非目标
- 是否有可执行的验收标准
- 是否标出相关模块、文档和测试方式

如果以上任一项缺失，先补 issue，再开始实现。

## 输出要求

当用户让你“写一个 issue”时，优先输出：

1. 一个合格的 issue 标题
2. 一份可直接粘贴到 GitHub 的 Markdown 正文
3. 如有必要，补一段“建议拆分为 2~N 个 issue”的说明

如果用户要求直接创建 issue，再基于这份结构调用对应工具或命令，不要跳过整理步骤。

## 触发示例

以下表达都应该触发这个 skill：

- “帮我把这个需求整理成 issue”
- “这个 bug 想建一张卡，你帮我补完整描述”
- “把账单模块拆成几个可执行 issue”
- “现在这个 issue 太空了，帮我补验收标准”
