# GitHub Issue 使用规范

本规范用于统一 Apartment Ultra 项目中 GitHub Issue 的写法和使用方式，避免 issue 只有一句需求、没有边界和验收标准，导致后续实现偏航。

## 目标

- 让 issue 成为项目任务的统一入口
- 让开发、评审、测试都能从 issue 获得足够上下文
- 让“完成”具备可验证的标准，而不是主观判断

## 什么时候应该建 Issue

以下情况默认应该建 issue：

- 新功能或流程调整
- 缺陷修复
- 会影响业务行为、接口契约、页面文案或测试预期的改动
- 跨模块的重构、技术债清理、基础设施调整
- 需要排期、跟踪、交接或回顾的工作

以下情况可以不单独建 issue：

- 纯格式修正、明显笔误
- 不影响行为的极小文档修订
- 已经在当前 issue 的明确范围内、且不会扩边的小修小补

如有疑问，默认倾向于建 issue，但前提是内容必须完整，不要创建空壳任务。

## 基本原则

1. 一个 issue 只描述一个明确结果。
2. issue 应该优先表达“结果”和“边界”，而不是零散想法。
3. 能否开工的判断标准，不是“有个标题”，而是“能否据此验收”。
4. 超过单次小改动范围的内容，要拆分成多个 issue。
5. PR、文档、测试和 issue 要互相可追溯。

## 标题规范

统一格式：

```text
[模块] 动作 + 结果
```

推荐模块值：

- `api`
- `tenant-web`
- `admin-web`
- `mobile`
- `packages`
- `e2e`
- `docs`
- `infra`

示例：

- `[tenant-web] 支持账单列表按状态筛选`
- `[api] 修复账单重复生成问题`
- `[admin-web] 补充服务定价分页查询`
- `[e2e] 覆盖租客续租与终止流程`

避免使用：

- `修复 bug`
- `优化功能`
- `处理一下租约`
- `支持某个需求`

## 正文模板

创建 issue 时，默认使用以下模板：

```md
## 概要
- 类型：feature | bug | refactor | chore | docs
- 模块：api | tenant-web | admin-web | mobile | packages | e2e | docs | infra
- 优先级：P0 | P1 | P2 | P3

## 背景
说明当前问题、触发场景或业务动机。

## 目标
说明这次要达成的结果。

## 范围
- 包含：
- 包含：

## 非目标
- 不包含：
- 不包含：

## 实现线索
- 涉及模块：
- 可能相关文件/文档：
- 上下游依赖：

## 验收标准
- [ ] 可被验证的结果 1
- [ ] 可被验证的结果 2

## 验证方式
- 单测 / 集成测试 / E2E / 手工验证
- 需要关注的边界条件

## 风险与依赖
- 风险：
- 依赖：

## 关联
- 关联文档：
- 关联 PR / Issue：
```

## 不同类型的补充要求

### Bug

除通用模板外，补充以下信息：

- 实际结果
- 期望结果
- 复现步骤
- 是否稳定复现

### Feature

优先写清：

- 谁会使用这个能力
- 业务收益是什么
- 完成后用户能做什么

### Refactor / Chore

优先写清：

- 当前痛点是什么
- 这次整理或重构做到哪里为止
- 如何验证没有引入回归

## 拆分规则

出现以下情况时，应拆分 issue：

- 同时涉及后端、前端、测试，且每部分都可以独立交付
- 同时混合“修 bug”“补功能”“顺手重构”
- 单个 issue 写不出清晰边界
- 单个 issue 预计需要多个 PR 才能安全落地

建议保留一个父 issue 描述背景与顺序，再用子 issue 承接具体交付。

## 开工前检查

开始实现前，至少确认：

- 标题是否清楚表达结果
- 是否写明范围与非目标
- 是否存在明确验收标准
- 是否写明验证方式
- 是否给出相关模块、文档或测试线索

如果以上任一项缺失，优先补全 issue，再进入实现。

## 完成后的回写要求

Issue 完成后，建议至少补回：

- 最终实现范围
- 实际验证方式
- 对应 PR 链接
- 未覆盖但已明确延期的后续项

这样可以避免 issue 在关闭后失去复盘价值。

## 推荐使用方式

如果由 Agent 协助处理 issue，建议直接用自然语言提出以下类型的请求：

- “帮我把这个需求整理成一个 issue”
- “把这个 bug 补成可以开工的 issue”
- “把这个大任务拆成 3 个 issue”
- “检查这个 issue 是否缺少验收标准”

项目内对应的协作 skill 位于 [`.claude/skills/issue-management/SKILL.md`](../.claude/skills/issue-management/SKILL.md)。
